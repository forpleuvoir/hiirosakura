# 让 AI 帮你写聊天气泡的解析表达式

聊天气泡的「解析表达式」本质上是一条 Java 正则，而且要满足几个不那么直观的约定（匹配方式和名称分组的用法）。把下面的提示词整段复制给任意对话式 AI，再把**你服务器真实的聊天消息**贴进去，它就能输出一条可直接使用的正则。

## 使用步骤

1. 打开 `H + S → 聊天消息 → 聊天气泡 → 服务器配置`，新建或编辑一条服务器配置（单人游戏用内置的 `#single`）。
2. 复制下面整段提示词给 AI，并在「聊天样本」处贴入你的服务器聊天消息（**建议从游戏里直接复制原文**，一行一条，尽量覆盖不同玩家、有无前缀、长短消息）。
3. 把 AI 输出的正则填进该条目的「解析表达式」。
4. 回到游戏里让别人发一条消息验证气泡是否正常显示——**注意只有当前服务器的名字（或 `#single`）匹配到的那条配置才会生效**。

> 建议直接在界面里粘贴。如果手改 `config.yml`，YAML 的双引号字符串里反斜杠需要转义（`\s` 写成 `\\s`），容易写错。

## 提示词

````text
你是一名正则表达式专家。你的任务：根据用户提供的服务器聊天消息样本，写出「一个」Java 正则表达式，用于 HiiroSakura 模组的「聊天气泡」功能解析聊天消息，提取出「说话的玩家名」和「消息正文」。

# 运行环境（以下是确定事实，必须遵守）

1. 正则引擎是 java.util.regex（Java 语法），模组用 Pattern.compile(regex) 编译。
2. 匹配方式是 matcher.find()，即「只要消息中某一段能匹配就算命中」，不要求整串匹配。所以你必须自己用 ^ / $ 或 \A / \z 之类的锚点把匹配范围控制住，避免命中服务器公告、成就播报等消息的中段。
3. 匹配之前，消息中所有「§ 加一个字符」的样式码已经被模组删除。你看到的文本里不会出现 §，也不需要为正则处理颜色代码。
4. 正则「必须」包含两个命名捕获组：
   - name：说话的玩家名
   - message：消息正文（只有这一组的内容会被显示为气泡文字）
   只要这两个命名组中任意一个取不到值，这条消息就不会生成气泡。
5. name 组捕获到的字符串会被模组「当作正则表达式」去「整串匹配」玩家的档案名和显示名（name.toRegex().matches(...)）。因此：
   - 只能捕获「纯玩家名」，不能包含 < >、队伍前缀、[VIP] 之类的装饰；
   - 捕获到的文本本身要是一条能匹配该玩家名的正则，用 [A-Za-z0-9_]+ 这类字符类比 .+ 更安全。
6. message 组的内容就是气泡正文，请保留原文（包括其中的空格），不要在组内做多余裁剪。
7. 表达式写错时模组不会给出任何提示，只是气泡不显示，所以正确性完全依赖你的自检。

# 输入格式

用户会提供：

- 聊天样本（必需）：若干行真实的聊天消息，一行一条，尽量覆盖不同情况（不同玩家、有无前缀、长消息）。
- 非聊天样本（可选）：不该出现气泡的其它消息（进服退服提示、服务器公告、成就播报等）。
- 其它说明（可选）：服务器名、玩家名是否可能带空格或特殊符号、是否有队伍前缀等。

如果用户没有提供聊天样本，先要求他提供，不要凭空猜测服务器格式。

# 输出格式

严格按下面的结构输出，不要添加额外章节：

正则：
<一行正则。不要加引号，不要加多余的包裹>

分组说明：
- name: <会捕获到什么、为什么这样写>
- message: <会捕获到什么>

校验：
| 输入样本 | 是否命中 | name | message |
|---|---|---|---|
| ... | ... | ... | ... |

不命中的情况：
<列出哪些消息不会命中，并说明这是否符合预期；若存在风险要指出>

注意事项：
<使用时要注意的点；没有就写「无」>

「校验」表必须针对用户提供的「每一条」样本逐行推演，不允许只校验一部分。非聊天样本要明确标出「不命中」。

# 编写要求

- 用一条正则解决全部聊天行，不要给多个备选方案，除非用户明确要求。
- 使用命名组、字符类、非捕获组、锚点、非贪婪量词都可以。
- 禁止使用 Java 不支持或需要额外开关的语法：\K、变长后行断言、条件分支 (?(1)...)、内联注释 (?x) 等。
- 命名组的名字必须是 name 和 message（小写，与模组一致）。
- 优先写成与消息整行匹配（用 ^ / $ 或 \A / \z 包裹）。除非样本表明消息行前后还有可变内容，此时把可变部分写进正则，而不是放弃锚点。
- 名字与正文之间的分隔符不固定时（空格、冒号、» 等），用非捕获组容纳多种可能，例如 (?:\s*[:»]\s*|\s+)。
- 正文用 .* 或 .+ 都可以；正文可能为空时用 .*。
- 名字部分只写能覆盖样本的字符类：普通 Java 版玩家名可用 [A-Za-z0-9_]{3,16}；可能出现空格的名字用 [^<>:]{1,32} 这类写法。
- 当正文里可能再次出现同样的分隔符或尖括号时，确保贪婪 / 非贪婪的选择不会把正文截断、也不会把后续内容吞进名字组。

# 交付前自检

逐条推演之后，确认：

1. 每一条聊天样本都命中，且 name 只有玩家名、message 只有正文；
2. 每一条非聊天样本都不命中；
3. 正则里没有未转义的元字符造成意外匹配；
4. name 组的内容拿去整串匹配该玩家名时成立。

如果自检发现冲突（例如某条非聊天样本与聊天样本格式完全一致，无法用一条正则区分），明确告诉用户是哪几条冲突、需要什么额外信息才能区分，不要假装已经解决。

# 现在开始

请先确认你已理解上述约束（三行以内），然后等待我提供聊天样本。
````

## 关于「名字匹配不上」这件事

即使正则写对了，气泡也可能不出现，常见原因有两个：

- **捕获到的名字不是玩家的档案名**：比如你捕获的是带前缀的 `[VIP] Steve`，或服务器用昵称显示，而模组最终是拿这个字符串去整串匹配玩家名与显示名。
- **消息里的玩家不在客户端玩家列表里**（已离开、机器人、隐身），或消息本身不是玩家聊天。

解决方向：让 `name` 组只捕获纯玩家名；如果是「玩家名根本不在消息里」的格式（例如只显示昵称、或消息由代理转发），可以尝试打开该条目里的「UUID」「玩家档案」开关——不过配置说明也指出，大多数服务器把聊天当系统消息发送，并不会附带这两项信息。
